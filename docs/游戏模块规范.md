# 游戏模块规范（src/games/）

「纯净玩」要装多款游戏。为了让每个游戏**独立开发、互不干扰**，约定如下。

---

## 1. 目录与文件

```
src/games/<gameId>/
├── index.js     模块入口：导出 meta 与 createSession
├── core.js      纯逻辑（可被 Node 直接 import 测试，禁止引用 canvas / wx / DOM）
├── render.js    绘制（只接收 ctx + layout + state，不持有状态）
└── test.mjs     该游戏的核心逻辑测试（node src/games/<gameId>/test.mjs 必须全过）
```

共享文件（**游戏模块不得修改**，由集成层负责）：
`src/app.js`、`src/ui/*.js`、`src/audio/*.js`、`game.js`

---

## 2. meta（大厅与难度页读它）

```js
export const meta = {
  id: 'minesweeper',              // 目录名一致
  name: '扫雷',                    // 大厅卡片标题
  desc: '经典推理 · 三种难度',       // 大厅卡片副标题（≤16 字）
  glyph: '雷',                     // 大厅图标里的单字
  ready: true,                     // 是否可进入
  // 难度档位（2–5 个）。集成层据此渲染难度页。
  difficulties: [
    { key: 'easy',   name: '初级', desc: '9×9 · 10 雷' },
    { key: 'medium', name: '中级', desc: '12×12 · 25 雷' },
    { key: 'hard',   name: '高级', desc: '16×16 · 50 雷' },
  ],
};
```

**棋类**（中国象棋/国际象棋/围棋）的难度表示 **AI 强度**，用统一命名：
`简单 / 普通 / 困难 / 地狱 / 亚洲`（与五子棋一致，key 用 `lv1`…`lv5`）。

## 3. createSession —— 集成层唯一调用入口

```js
export function createSession(options) {
  // options: { width, height, insets, difficulty, theme, onEvent }
  //   width/height 逻辑像素；insets = { top, bottom } 安全区
  //   difficulty   当前难度档位的 key
  //   theme        对局主题令牌（src/ui/theme.js 的 THEME）
  //   onEvent(type, payload)  可选：向集成层上报（如 'win' / 'lose' / 'score'）

  return {
    // 屏幕尺寸变化（旋转 / 不同机型）。游戏自己算内部布局。
    resize(width, height, insets) {},

    // 交互。坐标是逻辑像素，已含 insets 让位；游戏自己判断是否落在自己的控件上。
    tap(x, y, now) {},       // 一次点击（抬起）
    press(x, y) {},          // 按下（做按压反馈）
    release() {},            // 抬起（清除按压态）
    hover(x, y) {},          // 悬停（鼠标环境，可忽略）

    // 每帧推进（动画 / AI / 计时）
    update(now) {},

    // 绘制整屏（背景、棋盘/网格、HUD、按钮都由游戏自己画）
    render(ctx, now) {},

    // 顶部信息（集成层不画 HUD，由游戏自绘；这里只给外部读取用）
    get hud() { return { title: '扫雷', status: '剩余 10 雷', right: '00:32' }; },

    // 是否需要持续推帧（true 时集成层会一直 requestAnimationFrame）
    get busy() { return false; },

    // 可选：本局结果（用于集成层计分/提示）。没有结果时返回 null。
    get outcome() { return null; },   // 或 { result: 'win' | 'lose' | 'draw', score: 0 }

    // 可选：销毁（清理定时器等）
    destroy() {},
  };
}
```

## 4. 必须遵守的硬约束

1. **零依赖**：不 import 任何第三方包。
2. **无平台 API**：`core.js` 里禁止出现 `wx`、`document`、`window`、`canvas`；`render.js` 只接收传入的 `ctx`。
3. **ES Module**：用 `import` / `export`，文件后缀 `.js`（测试用 `.mjs`）。
4. **中文注释**：与现有代码风格一致（参考 `src/core/board.js`、`src/ui/renderer.js`）。
5. **测试必须通过**：`node src/games/<id>/test.mjs` 要输出 `通过 N 项，失败 0 项` 并以 0 退出。
6. **语法自检**：每个文件都要能通过 `node --check`。
7. **绘制用主题令牌**：颜色从传入的 `theme` 取（如 `theme.accent`、`theme.textPrimary`、`theme.gridLine`），不要写死一堆魔法色值；需要新颜色时用 `theme` 里已有的近似色。
8. **可重开**：会话内要有「重新开始」入口（画在屏幕内的按钮或由集成层提供，见下）。

## 5. 关于底部按钮与返回

- **返回按钮**（左上角）与**齿轮**（右上角）由**集成层绘制**，并用 `insets` 让位安全区。游戏模块**不要**在自己左上/右上角画东西，避免重叠。
- 游戏自己的操作按钮请画在**底部区域**，并**留出至少 `insets.bottom + 16` 的底部空白**——实机底部有手势条，画太靠下会被遮挡（这个坑已经踩过）。
- 底部建议放 1–3 个胶囊按钮，样式参考 `src/ui/renderer.js` 的 `drawButtons`。

## 6. 性能要求

- `render` 每帧调用，避免在其中做重计算（如全盘搜索）；重计算放 `update` 里按需触发。
- 棋盘类游戏单帧绘制应在 3ms 内（15×15 网格 + 数十个棋子）。

- [ ] 没有 import 第三方包

## 8. 时间约定（踩过的坑，务必遵守）
集成层传给 `tap / press / hover / update` 的 `now`，是 **`Date.now()` 的绝对毫秒时间戳**（约 1.79e12）。

因此：

1. **模块内部任何 fallback 时钟也必须是 `Date.now()`**，绝不要用 `performance.now()`
   —— 后者是"页面加载后的相对毫秒"（可能只有几十），两者相减会得到 1.79e12 这种天文数字。
   实测事故：扫雷计时器显示 `497361:46:00`。
2. **`now` 必须从入口一路透传到底**。漏传参数会静默使用默认值 `0`，同样导致计时从 1970 年算起。
   实测事故：`index.js` 调 `sessionReveal(session, gx, gy)` 时忘了带 `now`。
3. 涉及 `now` 的逻辑（计时、动画、AI 时间预算）**要写进测试**：用显式注入的时间戳断言，
   例如「传入 N 与 N+3000 后，用时显示 00:03」——扫雷的 203 项测试就是因为没覆盖这条而漏掉了上面的 bug。

## 9. 结算后不要自动重开（否则会把统一弹窗顶掉）

集成层在一局结束时统一弹窗（**再来一局 / 回到主界面 / 可叉掉**）。因此：

- **游戏模块不得在结算后自动 restart()**。
  实测事故：扫雷结算 1.5 秒后自动重开，`outcome` 随即变回 `null`，
  集成层的弹窗刚淡入就被顶掉，用户根本来不及点。
- 结算后只需**保持终局画面**并把 `outcome` 一直返回，直到集成层调用 `destroy()` 或重建会话。
- 结算动画（爆炸、连线高亮等）可以继续跑，但**不要据此重开局**。

## 10. 边界约定（集成层提供什么、你提供什么）

| 能力 | 由谁提供 |
|---|---|
| 全屏青白渐变背景 | **集成层**（用 THEME.bgTop/bgMid/bgBottom），游戏不要自己铺满屏 |
| **清屏（clearRect）** | **集成层**。游戏**不要**调用 clearRect(0,0,w,h)——实测事故：蜘蛛纸牌有一句 clearRect，把集成层刚铺好的青白底清掉，整个画面露出页面深色背景（实机截图表现为整屏深灰）。 |
| 左上返回键、右上齿轮 | **集成层**（游戏不要画；顶部同高度留空，避免遮挡） |
| 统一结算弹窗 | **集成层**（游戏只返回 outcome） |
| 木质按钮外观 | 集成层导出的 drawWoodButton（src/ui/renderer.js），游戏调用它画自己的操作按钮 |
| 文字颜色 | 一律取 theme.* 令牌；**不要写死颜色**（深色主题的浅字在青白底上会直接消失） |
| 顶部空间 | 游戏 HUD 请从 insets.top + 8 往下排，并避开左上/右上各约 56px 的区域 |

## 11. Canvas 变换卫生（血泪教训）

任何一处 `save()` / `restore()` 不配对，或 `translate()` 前忘了 `save()`，
都会让变换**逐帧累积**：实测 `drawGearButton` 漏了一个 `save()`，
平移量涨到 **990 万像素**，画面只剩边角。

- 每个 `translate/rotate/scale` 都必须被 `save()/restore()` 包住。
- 集成层已在每帧渲染前后重置变换作为兜底，但**游戏模块自己也要写干净**。

## 12. 测试必须消除随机性（否则 flaky，交付不算数）

**实测事故**：蜘蛛纸牌的 373 项测试里，有 2 项依赖真实洗牌（`Math.random`），
我连跑 5 次的结果在「0 失败」到「2 失败」之间波动 —— 而开发者自报是「373 项全过」。
这类测试**不能作为交付依据**。

要求：

1. **随机逻辑必须可注入随机源**：洗牌、生成题面、抽牌等一律提供 `random` 参数
   （推荐内置 `mulberry32(seed)`），测试传固定种子。
   —— 这与第 8 节「时间必须可注入」是同一类要求。
2. **断言不要依赖"随机恰好有解"**：先**扫描出**一个合法操作，再断言「执行后状态确实变化」；
   确实无解的局面要能**识别并跳过**，而不是判失败。
3. **交付前连跑 10 次**，10 次全绿（失败 0 项、退出码 0）才算通过。
   单次通过不能证明测试稳定。
